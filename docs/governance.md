# 项目治理与支持

## 决策方式

- 兼容承诺、最低 Java 版本、namespace、公开 API 和安全边界的变化必须记录 ADR。
- 可逆实现细节由维护者评审后合并；跨主版本行为不能通过 patch/minor 版本偷渡。
- 性能宣传以可复现报告为准，负结果和环境限制与正结果一起保留。
- 真实业务兼容修复必须抽象成标准行为或通用缺陷，不把业务仓库耦合进容器。

## 版本与维护

- `1.x` 长期维护 Java 8 / `javax.servlet` / Servlet 3.1，只接受安全、容器缺陷和旧项目兼容修复。
- `main` 在发布 1.0 后演进 Java 17 / `jakarta.servlet` 的 2.x。
- 共享缺陷先修复最老的受影响维护线，再前向合并。
- 弃用行为至少在一个 minor 版本的变更记录中说明；安全紧急修复可例外，但必须补记录。

## Issue 分流

公开问题至少提供 tinysc 版本、JDK、操作系统、最小复现、期望/实际结果和脱敏日志。以下内容
不进入公开 Issue：凭据、业务数据、未披露漏洞、内网地址和未经授权的第三方源码。

当前尚未建立公共 Issue Tracker、邮件列表、漏洞邮箱、维护者名单和响应 SLA；开源发布前必须
由项目所有者补齐这些可联系信息。

## 开源发布门禁

本仓库目前没有由项目所有者确认的开源许可证，因此源码可供当前工作区开发验证，但不能据此
推定获得对外复制、修改或再发布授权。首次公开发布前必须：

1. 由项目所有者选定并添加许可证文本与版权声明；
2. 审核所有直接/传递依赖的许可证并生成 SBOM；
3. 建立安全报告渠道、维护者清单和发布签名策略；
4. 确认 Probe、基准数据和文档不含业务代码、配置、凭据或内部地址。
