# ADR-0009：有界弹性工作线程池

## 状态

Accepted

## 背景

1.x 的 HTTP 入口已经把 Netty I/O 线程和应用执行线程分离，但固定数量的 worker 池在突发流量下要么
过早排队，要么在低谷期浪费资源。作为 1.x 的 P0 并发决策，需要一套可解释、可回退的线程调度
规则。

本决策只覆盖 worker 调度与排队，不解决请求字节级准入控制或流式上传；这一部分保留到后续阶段。

## 决策

- `--workers` 表示 worker 池上限，不再表示固定线程数。
- `--min-workers` 默认为 `min(8, --workers)`，作为已创建线程的核心保留线；容器不会仅为
  凑足该数量而预启动线程。
- `--worker-idle-timeout` 默认为 `60` 秒；超过核心保留线的空闲 worker 在超时后被回收。
- `--worker-queue` 默认从 `1024` 收紧为 `100`；显式配置继续按调用方给定值生效。
- 队列保持有界。现有 worker 都繁忙且未触顶时优先扩容；存在空闲 worker 时，请求可以短暂
  入队并立即被消费。
- Netty I/O 线程不使用 `CallerRuns` 兜底，避免把业务阻塞带回接入线程。
- 当 worker 和队列同时饱和时，对外返回 `503`。

## 验收门禁

- 空闲超时后，worker 数应回落到不超过 `min-workers`。
- `max-workers + queue` 必须保持有界，不能出现无界累积。
- 压力解除后，系统应从饱和态恢复，重新接受新请求。

## 后果

### 正面

- 短突发下不会过早把请求压到无界队列里。
- 线程和排队上界清晰，便于容量推导和故障控制。
- `503` 作为统一过载信号，便于上游治理和限流。

### 负面

- 需要维护动态伸缩与回收逻辑。
- 高峰下仍会拒绝请求，不能把容量上限伪装成无限吞吐。
- 该决策不解决请求体字节级准入和流式处理，上传类场景仍然受限。

## 备选方案

- 固定 worker 池加无界队列：拒绝，因为尾延迟和内存风险都不可控。
- 固定 worker 池加 `CallerRuns`：拒绝，因为会把 Netty I/O 线程拖入业务阻塞。
- 只提高 worker 数量、不设上限：拒绝，因为这会把过载推迟到资源耗尽阶段。
